# Systems-Design Audit — Dungeon Dash

Scope: combat math, stat derivation, progression curves, upgrade/loot economy,
class differentiation. Code is truth; `docs/GAME_DESIGN.md` is checked as
current intent, `DungeonDash_DesignBrief.md` as historical (expected drift).

## What exists

- **4 classes**, `DD.CLASSES` (`js/entities.js:16-41`) — Warrior 12hp/165spd/melee dmg3/cd0.50/range46/arc2.4; Rogue 8/225/melee dmg2/cd0.51/range34/arc1.5/dash; Mage 6/160/bolt dmg3/cd0.50/projSpeed380/splash38; Ranger 8/185/arrow dmg2/cd0.64/projSpeed540/pierce1.
- **Stat pipeline**: `DD.deriveStats` (`js/stats.js:7-43`) turns hero persistent data into `baseStats` — class base + `(level-1)*growth` + attribute scaling + flat gear mods. `Player.recompute()` (`js/entities.js:132-146`) then multiplies `baseStats` by run-scoped `runBuffs` to get live `stats`. Formulas: `dmg = base + (lvl-1)*0.15 + might*0.5`; `speed = base + (lvl-1)*2 + agility*5`; `hp = base + (lvl-1)*0.5 + vitality*1.5`; `cooldown = max(0.08, base - agility*0.01)`; focus feeds `range/arc/projSpeed/splash`. One attribute point granted per level-up (`js/game.js:1516-1518`), spent freely by the player.
- **Damage resolution**: `effDmg() = Math.max(1, Math.round(stats.dmg))` (`js/entities.js:150-152`) — every hit rounds to an integer. Melee is an **instant hitscan cone** that damages every qualifying enemy in range+arc in one frame, no travel time, no per-target cooldown (`js/entities.js:250-264`). Player damage taken is flat subtraction with no mitigation stat (`js/entities.js:282-303`); only `maxHp` buffers survivability. i-frames fixed at 0.9s for every class.
- **6 run upgrades**, `DD.UPGRADES` (`js/entities.js:45-76`): dmg ×1.3, speed ×1.15, +3 maxHP (+heal3), cooldown ×0.8 (floor 0.08), reach (class-dependent: melee range×1.25/arc×1.12; bolt splash×1.35/projSpeed×1.1; arrow pierce+1/projSpeed×1.1), siphon +0.3 heal-on-kill chance. 3 of the 6 drawn at random per level-up, fresh pool each time (`js/game.js:1487-1499`).
- **XP curve**: `xpNext() = 25 + (level-1)*15`, linear (`js/game.js:197`). Cumulative XP to level *L* = `25(L-1) + 7.5(L-1)(L-2)`. Tier gates `TIER_REQ = [1, 11, 21]` (`js/game.js:131`), tiers span levels 1-10/11-20/21-30. Level and XP are **persistent on the hero**, not reset per run (`startFloorRun`, `js/game.js:329-330`; `endRun`, `js/game.js:721-722`).
- **Tier scaling**, `DUNGEONS` (`js/game.js:48-110`): per-dungeon `scale` multiplier applied to enemy HP/speed only, roughly 1.0/3.0/6.0 (Catacombs) up to 1.2/3.6/7.0 (Crypt); boss HP 70→160→280 (Catacombs) up to 90→190→320 (Crypt); boss `dmg` config 2→4→7 up to 3→5→9.
- **Enemy stat table** — `Skeleton` constructor (`js/entities.js:562-660`): per-kind base HP/speed/dmg/xpValue/coinDrop, `hp = round(baseHp * scale)` (`entities.js:589`) and `speed` lightly scaled (`entities.js:605`), but **`xpValue` and `coinDrop` are never multiplied by `scale`** (`entities.js:606-624` — no `scale` term anywhere in either expression).
- **Enemy grades**, `DD.rollGrade` (`js/entities.js:536-549`): regular/veteran(×1.6hp, `Math.ceil(dmg*1.35)`)/elite(×2.8hp, `Math.ceil(dmg*2.0)`, ×2 xp) — HP uses `Math.round`, damage uses `Math.ceil` (`entities.js:627-638`), an inconsistent rounding rule between the two.
- **One shared `Boss` class** (`js/entities.js:1006-1113`) for every dungeon's boss. `xpValue: 40` and `coinDrop: [12, 18]` are **hardcoded in the constructor** (`entities.js:1014-1015`), ignoring the tier-scaled `bossHp`/`bossDmg` passed in via `opts`. The boss's telegraphed slam — its signature, highest-damage attack — also hardcodes `p.damage(2, ...)` (`entities.js:1058`) regardless of `this.dmg` (the tier-scaled value from `cfg.bossDmg`); only the boss's inherited generic melee-contact damage (via the base `Skeleton` chase→windup state machine, since `Boss` never overrides `kind` and defaults to `"melee"`) actually uses the scaled `this.dmg`. `bossName`/`bossHp`/`bossDmg` are keyed by **tier only, not floor** (`dungeonFloorCfg`, `js/game.js:114-128`, spreads `tier` after `flr`) — all 3 floor-ending boss fights in one dungeon+tier are numerically and nominally identical.
- **21 items**, `ITEM_BASES` (`js/items.js:25-53`), 3 rarities as pure multipliers on mod values — common ×1.0/rare ×1.6/epic ×2.5, weights 60/28/12 (`js/items.js:19-23`). Buy 25/70/150, sell 10/30/60 (`js/items.js:7-8`). `item.levelReq` is hardcoded to `1` at roll time (`js/items.js:108`) and grepped nowhere else in the codebase — dead field. Inventory cap 15 (`js/items.js:3`). Trader restocks 5 random items every town visit (`js/game.js:1041`).
- **Dead enemy kinds**: `shade` and skeleton `bomber` have full stat/AI/sprite branches in `Skeleton` (`entities.js:578-624, 670-671, 821-830, 903-905, 952-973`) but **no `DUNGEONS.*.floors[*].kinds` or `eliteKinds` array anywhere lists `"shade"` or `"bomber"`** (verified against all `kinds:`/`eliteKinds:` entries, `js/game.js:57-101,1337-1338`) — they can never spawn through normal play.
- **Dead in-dungeon shop**: `ShopItem`/shop room logic is fully built (`js/entities.js:1239-1306`, `js/game.js:649-660`), but **no dungeon's `plan` array contains `"shop"`** anywhere in `DUNGEONS` (`js/game.js:56-109, 1337`), and floor-mode additionally filters it out explicitly (`loadFloor`, `js/game.js:342`). The shop-between-floors room type is unreachable in both run modes.
- **Quest rewards**, `QUEST_DEFS` (`js/profile.js:116-127`) — 10 quests, 20g-250g gold (+0-90 bonus XP), max 3 active (`ACTIVE_CAP=3`), abandoning costs 100g (`ABANDON_COST`, `js/profile.js:27-28`).
- **Economy**: gold is banked only on a won run (`endRun`, `js/game.js:724`); death forfeits the run's gold. Persistent hero never loses level/XP/gear — no permadeath (matches `docs/GAME_DESIGN.md` intent).

## What's solid

- **The stat pipeline is clean and correctly layered.** `deriveStats` → `baseStats` (persistent: class + level + attrs + gear, all additive) → `Player.recompute()` multiplies by `runBuffs` (run-scoped, reset every run) → `stats`. The doc comment in `stats.js:6` even states the parity guarantee ("level 1, no attrs, no gear = `{...DD.CLASSES[classKey]}`") and it holds on inspection. Run power never leaking onto the persistent hero (per the file header comment, `entities.js:43-44`) is real and enforced structurally, not just by convention.
- **The rarity/price system is a coherent, self-consistent design**: multiplicative scale-on-mods (1.0/1.6/2.5) with matching weight taper (60/28/12) and a buy>sell spread (~40% return) that makes gear churn a real gold sink without being punitive. This is small, well-scoped, and easy to reason about.
- **The economy roughly balances at the tier the numbers were clearly tuned for.** A full Catacombs Tier-1 (index 0) clear yields on the order of 200 gold (see arithmetic below) against 25/70/150 buy prices — affordable but not trivial. Quest rewards (20-250g) sit in the same range.
- **Class stat spreads read as intentional, not random**: Mage is lowest HP/highest burst-with-AoE, Ranger trades single-target DPS for pierce-through-groups, Warrior is the balanced high-HP baseline. The numbers back up the flavor text for 3 of 4 classes (see Rogue below for the exception).
- **XP curve is genuinely linear** (`25 + (level-1)*15`, no hidden curve-fitting), which is easy to reason about, easy to retune, and easy to verify against play data — a good property for a system this small.
- Grade multipliers (veteran/elite) are simple, multiplicative, and readable at a glance.

## What's rough, incomplete, or inconsistent

**1. Enemy/boss rewards don't scale with tier — only enemy toughness does.** This is the single largest problem I found. `hp = round(baseHp * scale)` and boss `hp`/`dmg` are tier-scaled (1.0×→6-7×), but `xpValue`, `coinDrop`, and the boss's hardcoded `xpValue:40`/`coinDrop:[12,18]` are not (`entities.js:606-624, 1014-1015`). Worked example — a Catacombs "melee" skeleton (`baseHp=6`) across tiers, Warrior at level 1 with `effDmg=3`, `cooldown=0.5`, melee is instant-hit so `TTK = (hits-1) * cooldown`:

  | Tier | scale | enemy HP | hits to kill | TTK | XP reward |
  |---|---|---|---|---|---|
  | 1 (idx0) | 1.0 | 6 | 2 | 0.5s | 5 |
  | 2 (idx1) | 3.0 | 18 | 6 | 2.5s | 5 |
  | 3 (idx2) | 6.0 | 36 | 12 | 5.5s | 5 |

  TTK grows **11×** from Tier 1 to Tier 3 for the *identical* reward. Even a well-built Tier-3-eligible character (level 21, all 20 attribute points into might: `dmg = 3 + 20*0.15... wait` — concretely `dmg = 3 + (21-1)*0.15 + 20*0.5 = 3 + 3.0 + 10 = 16`, `effDmg=16`) still takes `ceil(36/16)=3` hits → 1.0s TTK vs. 0.5s at Tier 1 baseline — roughly **2× slower per kill for the same 5 XP / 1-3 gold**. The boss case is starker: Catacombs boss HP goes 70→160→280 across tiers while `xpValue`/`coinDrop` stay flat at 40/[12,18] regardless (`entities.js:1014-1015`) — a Tier-3 boss with 4× the HP of a Tier-1 boss gives the exact same reward. **Net effect: once Tier 2/3 are unlocked, farming Tier 1 is strictly more XP- and gold-efficient per second than playing the tier you unlocked**, for every class. This isn't a subtle tuning nit; it removes the mechanical incentive to engage with harder content at all.

**2. `effDmg`'s `Math.round()` creates real dead zones in the might/gear investment.** Because `Math.round` snaps to the nearest integer and might adds a flat `+0.5` per point (`stats.js:22`), consecutive attribute points alternate between "free +1 damage" and "no measurable effect until the next point": e.g. Warrior base `dmg=3` — point 1: `3.5→round 4` (+1 realized); point 2: `4.0→round 4` (0 realized); point 3: `4.5→round 5` (+1); point 4: `5.0→round 5` (0). Roughly half of all might investment (in isolation, before run-upgrade multipliers) produces zero combat effect until compounded by a second point. The same rounding gap applies to the "Sharpened Edge" (+30% dmg) run-upgrade when stacked at low base damage — e.g. `dmg=2 → 2.6→round 3` (+1), next stack `2.6*1.3=3.38→round 3` (0 realized) — so upgrade value is not uniform across the stat range, and the game gives the player zero visibility into where the breakpoints fall.

**3. "Sharpened Edge" (+30% dmg) strictly dominates "Quick Hands" (20% faster attack) as a DPS choice, with no offsetting downside for dmg.** DPS ≈ `effDmg / cooldown`; a dmg pick multiplies the numerator by 1.30, a cooldown pick multiplies the effective attack rate by `1/0.8 = 1.25`. **1.30 > 1.25 on every stack**, and cooldown additionally hits a hard floor (`Math.max(0.08, ...)`, `entities.js:138`) — e.g. from Warrior's base 0.5s cooldown, only ~8 stacks of ×0.8 remain useful before the floor (`0.5 * 0.8^n ≥ 0.08 → n ≤ 8.3`) while dmg has no such ceiling. Both are drawn from the same 6-upgrade, 3-shown pool every level-up, so a rational player picks dmg whenever offered (~50% of level-ups, by combinatorics: `C(5,3)/C(6,3) = 50%` chance it's *not* in a given draw of 3-of-6). Over a 29-level-up career (level 1→30) that's ~14-15 "always take it" picks — the level-up screen degenerates into "did I see Sharpened Edge" for close to half of all choices.

**4. Only 6 upgrades total for a 30-level progression, with no per-class or per-tier variety.** Every class, every level, draws from the same 6-entry pool (3 shown, fresh each time — `js/game.js:1490-1493`). With that few options and the dmg/cd asymmetry above, repeat exposure is high and the choice rarely feels new by level 20+. The "reach" upgrade is the only class-differentiated one (and only cosmetically — it's DPS-neutral utility, not comparable in raw power to dmg/cd), so class identity essentially stops being reinforced at level-up time after the initial class pick.

**5. Rogue is dominated by Warrior on every raw combat stat, with no compensating output.** Warrior: dmg3, cooldown**0.50**, range46, arc**2.4**rad(137°), hp12. Rogue: dmg2, cooldown**0.51** (marginally *slower*, not faster), range34, arc**1.5**rad(86°), hp8 (`entities.js:17-28`). Warrior wins damage, attack speed, melee range, cone width (i.e., innate free cleave against groups — melee is a hitscan cone that damages *every* qualifying enemy per swing, `entities.js:254-263`), and survivability, simultaneously. Rogue's only compensation is +36% move speed (225 vs 165) and a dash (1.6s cooldown, ~99px burst, 0.3s i-frames). That's a coherent mobility-vs-power identity on paper, but since player damage taken is flat subtraction with a fixed 0.9s i-frame for *every* class (`entities.js:285`) — i.e., there's no stat where Rogue's speed advantage converts into a mechanical defensive multiplier beyond what any class gets from dodging on foot — it's not obvious the speed/dash actually pays for the damage and cleave deficit. This reads as *undifferentiated-toward-strictly-worse* rather than merely unbalanced; worth a playtest-driven check, not just a numbers one.

**6. Boss identity is diluted by tier-only (not floor-only) scaling.** `dungeonFloorCfg()` merges the active floor's content with the active tier's stats (`js/game.js:118-128`), and `bossHp`/`bossDmg`/`bossName` all live on the *tier* object, not per-floor. Every dungeon has 3 floors, each capped by "its own boss" per the design doc language — but mechanically it's the same boss (same HP, same damage, same name) fought 3 times per tier, with zero escalation floor-to-floor. Whether that's fine pacing is level-design's call; the fact that the *values* don't escalate within a tier is mine to flag.

**7. Minor internal inconsistency**: veteran/elite grade multipliers round HP with `Math.round` but damage with `Math.ceil` (`entities.js:629-637`) — a small, needless asymmetry (elite damage is always rounded up, elite HP is rounded to nearest) with no apparent rationale.

**8. `item.levelReq` is a half-built feature.** Every rolled item gets `levelReq: 1` (`items.js:108`) and nothing in the codebase ever reads it — no gating on equip, no display. It's schema for a feature that was never wired up.

## Next steps

1. **Scale enemy/boss rewards with the same `scale`/tier factor already used for HP.** This is a small, surgical, high-leverage fix: multiply `xpValue` and `coinDrop` by (a fraction of) `scale` in the `Skeleton` constructor (`entities.js:606-624`), and pass `xpValue`/`coinDrop` into `Boss` from `cfg` instead of hardcoding `40`/`[12,18]` (`entities.js:1014-1015`), and route the boss slam's damage through `this.dmg` instead of the literal `2` (`entities.js:1058`). Without this, tier progression has no economic rationale — it's the single highest-value fix in this domain.
2. **Rebalance the "Quick Hands" cooldown upgrade (or nerf/re-scope "Sharpened Edge")** so the two aren't strictly ordered, and consider widening the upgrade pool (or making a subset class-specific) so a 29-level-up career doesn't converge on "always take damage." Cheap to do since `DD.UPGRADES` is a flat, well-isolated array.
3. **Decide Rogue's identity on purpose**: either give it a real damage-side or survivability-side compensation (e.g., its cooldown should plausibly be *faster* than Warrior's given the "lightning-fast stabs" flavor text, not slightly slower; entities.js:19 vs :25), or lean harder into mobility with a mechanic that actually converts speed into damage avoidance (e.g., a brief post-dash effect). Right now the numbers don't back the class fantasy.

## Salvage or rebuild?

**Keep and tune — do not rebuild this domain.** The architecture is the good news: `baseStats × runBuffs → stats` is a clean, correctly-layered pipeline with an enforced separation between persistent and run-scoped power (`entities.js:43-44, 132-146`), the rarity/price system is internally consistent, and the XP curve is a one-line formula anyone can retune by eye. None of the problems found here are structural — every one of them (reward scaling not following tier scale, the dmg/cd asymmetry, Rogue's stat spread, the boss-reward hardcoding, the rounding inconsistency) is a **data or formula fix in a handful of well-isolated tables** (`DD.CLASSES`, `DD.UPGRADES`, the `Skeleton`/`Boss` constructors, `DUNGEONS` tiers), not a redesign of how stats are computed or how progression is wired. The biggest finding (reward/tier decoupling) is a two-line change per call site once you know to look for it — I would not trade that fix for a rewrite.

What's worth carrying forward as-is: the class base stats and flavor differentiation for Warrior/Mage/Ranger (the numbers read as deliberate), the item rarity/price curve, the linear XP formula, the attribute/level-up split (1 attr point + 1 run upgrade per level, cleanly separated). What needs real rework, not just tuning, before calling this domain done: Rogue's stat spread relative to its class fantasy, and the upgrade pool's variety for a 30-level career — both are still numbers-only fixes, just bigger ones than a one-line multiplier. **Design intent and tuning values here would survive a full engine/stack rewrite with zero loss** — none of this depends on the rendering stack, the 3D layer, or any particular JS structure; it's arithmetic on plain objects.

## Discrepancies

- `docs/GAME_DESIGN.md:100-101` states Tier 2 unlocks "at level 10" and Tier 3 "at level 20." The actual `TIER_REQ = [1, 11, 21]` (`js/game.js:131`) requires level **11** and **21** — off by one in both cases.
- `docs/GAME_DESIGN.md:90` lists Catacombs enemies as "melee, archer, shade (wall-phaser)." Catacombs' actual roster is `["melee", "archer", "zombie", "warlock"]` (`js/game.js:57`) — `shade` is not in any Catacombs (or any) `kinds`/`eliteKinds` array in the game and can never spawn (see "What's rough" #5... i.e. dead-kind finding above); `zombie`/`warlock` are undocumented in that doc line.
- `docs/GAME_DESIGN.md:140-141` lists Trader and Quest Giver as "stub (coming soon)," but `docs/GAME_DESIGN.md:184-186` (Roadmap → Shipped) says both are ✅ shipped, and the code backs the shipped claim (`js/profile.js:116-198`, `js/game.js:1084-1172`). The doc contradicts itself; the NPC table (§6) is stale.
- `README.md:6` promises bosses "the Skeleton King, the Bone Emperor, and The Deathless" as if each dungeon's 3 floors have 3 distinct escalating bosses. The actual `bossName` is keyed by **tier**, not floor (`js/game.js:66-109`), so within one dungeon+tier the same boss (same name, same HP, same damage) is fought on all 3 floors; there is no "Bone Emperor" or "The Deathless" anywhere in `DUNGEONS` — those names don't exist in the code at all (dungeon boss names are "SKELETON KING," "GOBLIN WARLORD," "THE LICH").
- `README.md:79` and the (historical) `DungeonDash_DesignBrief.md:20,49,105` describe "a shop between floors" as a live feature. It exists in code (`entities.js:1239-1306`, `game.js:649-660`) but is unreachable — no `DUNGEONS` floor `plan` ever includes `"shop"`, and floor-mode explicitly filters the token out (`js/game.js:342`) even if one were added. This one is already flagged as a known dead path per the audit brief, not a new discovery, but it directly contradicts both docs' framing of it as playable.
- `DungeonDash_DesignBrief.md` (historical, per charter) describes gold "split 50/50 between players," per-class "ability upgrade trees (3 upgrades per class)," and enemy stats that "scale down" for solo play. None of that exists: gold is a single shared pool with no co-op split logic found in `js/game.js`'s gold handling, there are no per-class upgrade trees (one shared 6-entry pool for all classes, `entities.js:45-76`), and I found no solo-vs-co-op enemy stat scaling anywhere in `Skeleton`/`Boss` (`scale` comes only from dungeon tier, `js/game.js:114-128`). Expected drift per the brief's historical status — noted, not treated as a bug.

## Hand-offs

→ level-design: boss HP/dmg/name are identical across all 3 floors of a dungeon+tier (`js/game.js:114-128`) — floor-to-floor escalation within a tier is entirely flat; whether that's acceptable pacing is level-design's call.
→ level-design: enemy reward values not scaling with tier (systems fix, see Next Steps #1) means the *shape* of "should Tier 2/3 rooms contain more/tougher enemies for a bigger payoff" needs a level-design pass once rewards are corrected, so the payoff curve matches the encounter-density curve you already own.
→ ux-ui: nothing on the stat/hub screen (`js/game.js:799-852`) surfaces the `effDmg` rounding breakpoints (What's Rough #2) or the dmg-vs-cooldown upgrade asymmetry (#3) — players can't see why a might point or an upgrade pick "didn't do anything."
→ narrative: README's boss names ("Bone Emperor," "The Deathless") don't match any in-code `bossName` — either the README is stale or those names were meant to be wired in and never were; the class-vs-flavor mismatch on Rogue's cooldown (flavor says "lightning-fast," value says slower than Warrior) is also a narrative/systems seam worth a joint pass.
→ qa: `item.levelReq` is written on every item but read nowhere (`items.js:108`) — not a crash risk, but worth confirming it's genuinely dead and not silently mis-wired somewhere I didn't find via grep.
